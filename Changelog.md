# Changelog

## Unreleased

### Upgrade notes

These fixes reject input that 1.1.0 accepted or change how a running dataflow behaves. Each one replaces a crash, a hang, or a silent misconfiguration, but check them before upgrading. The ROS 2 service client change under Changed and the renamed C/C++ release assets under Fixed are upgrade notes too.

- **A repeated key in a hand-written YAML file is an error** ([#4145](https://github.com/dora-rs/dora/pull/4145), [#4188](https://github.com/dora-rs/dora/pull/4188)). YAML forbids duplicate keys, but the last entry of a map field silently won, so two `image:` lines under `inputs:` dropped the first subscription. Dataflow and module files, the YAML that `dora node add`/`replace` take, `dora-node.yml` manifests, `types/**/*.yml` files and `cluster.yml` now fail with the key and its location.
- **A node whose `cpu_affinity` cannot be applied exactly no longer starts** ([#4201](https://github.com/dora-rs/dora/pull/4201)). On Linux the mask was best effort: a core at or above `CPU_SETSIZE` was skipped, a failing `sched_setaffinity` only warned, and the kernel silently narrowed a mask with an offline, missing or out-of-cpuset core. The daemon now rejects an empty list and an out-of-range core before the spawn, and fails the spawn if the mask it reads back differs from the declared one. Other platforms are unchanged.
- **Runtime nodes and operator ids are checked when the dataflow is resolved.** A runtime node must hold exactly one operator; two used to pass `dora validate` and fail once the runtime started ([#3719](https://github.com/dora-rs/dora/pull/3719)). An operator id must be a valid output-id segment without `/`; an id such as `my op` used to crash the daemon, and every dataflow on it, at spawn ([#3729](https://github.com/dora-rs/dora/pull/3729)).
- **A `dora/logs/<level>/<node>` input must name a node that exists after module expansion** ([#3846](https://github.com/dora-rs/dora/pull/3846)). A filter naming a module was accepted and the sink silently received nothing; the error points at `<module>.<inner-node>`. A top-level `types/std.yml` is also rejected now, since it overwrote built-in `std/` types ([#3882](https://github.com/dora-rs/dora/pull/3882)).
- **A taken dynamic-node port is an error.** `dora run` fails when another process holds it and honours `DORA_DAEMON_LOCAL_LISTEN_PORT` ([#3815](https://github.com/dora-rs/dora/pull/3815)). A `dora up`/`dora daemon` daemon keeps starting, but refuses a dynamic node at spawn, `dora node add` and `dora node replace` with an error naming the port ([#3877](https://github.com/dora-rs/dora/pull/3877)). Dynamic nodes used to connect to whatever held the port, sometimes another dataflow.
- **Hub builds check more of what they resolve.** A `--hub-override` checkout must be the overridden `<namespace>/<name>` ([#3850](https://github.com/dora-rs/dora/pull/3850)), a hub package whose shipped type conflicts with an already registered one is rejected instead of silently dropped ([#3851](https://github.com/dora-rs/dora/pull/3851)), and `--locked` refuses a hub lockfile entry for a plain `git:` node ([#4183](https://github.com/dora-rs/dora/pull/4183)).
- **Some environment variables are bounded.** `DORA_ZERO_COPY_THRESHOLD` is capped at 32 KiB with a warning, since larger values sent mid-size payloads down a path that drops them ([#4111](https://github.com/dora-rs/dora/pull/4111)). `DORA_ZENOH_OPEN_TIMEOUT_MS=0` is ignored with a warning instead of failing every dial ([#4125](https://github.com/dora-rs/dora/pull/4125)). A `DORA_RUN_PARENT_PID` that is not a positive pid disables the orphan guard with a warning; a value above `i32::MAX` used to make the guard kill the node's own process group ([#4192](https://github.com/dora-rs/dora/pull/4192)).
- **A `node` path no longer resolves to a directory** ([#4185](https://github.com/dora-rs/dora/pull/4185), [#4237](https://github.com/dora-rs/dora/pull/4237)). A folder named like the executable, such as the `talker/` source folder next to `path: talker`, won over the uv and `$PATH` lookup and the spawn failed. A folder is still used when it has a `__main__.py` for `--uv`. This applies to `hub:` nodes too.
- **A direct-zenoh `drop_oldest` input holds at most `queue_size` messages in total** ([#3594](https://github.com/dora-rs/dora/pull/3594), [#4156](https://github.com/dora-rs/dora/pull/4156)). It used to hold up to a channel's worth of the producer's shared-memory chunks on top of its queue, which starved the producer's pool. A consumer slower than its producer now drops sooner, at the depth its `queue_size` says.
- **The C and C++ node APIs refuse a `UInt8` input with null slots** ([#3943](https://github.com/dora-rs/dora/pull/3943)). They used to hand out the bytes behind the null slots. C now returns no data (`NULL`, 0) and logs it; C++ returns an error.
- **The DDS ROS 2 bridge honours `ROS_DOMAIN_ID`** ([#2878](https://github.com/dora-rs/dora/pull/2878)). Every node used to join domain 0. Service and action endpoints are now reliable with `keep_last` 10 whatever the topic QoS says, and the action status channel is transient-local ([#4232](https://github.com/dora-rs/dora/pull/4232)), so real ROS 2 peers match them. A `ROS_DISTRO` whose GID width differs from the build fails the DDS context at creation ([#4226](https://github.com/dora-rs/dora/pull/4226)).
- **`dora self update` refuses the cases it cannot do.** A CLI installed from the `dora-rs-cli` wheel points to `pip install -U dora-rs-cli` (or uv/pipx) instead of overwriting the interpreter ([#4233](https://github.com/dora-rs/dora/pull/4233)), and a target with no prebuilt CLI points to `cargo install dora-cli` instead of downloading another platform's archive ([#4169](https://github.com/dora-rs/dora/pull/4169)).
- **`deploy.distribute: scp` and `http` do not transfer binaries** ([#4223](https://github.com/dora-rs/dora/pull/4223)). They behave like `local`, and the CLI now warns when a dataflow uses them. The coordinator's unused HTTP artifact endpoint is removed. The docs used to describe both values as transferring the built binary.

### Added

- **dora nodes can read and tune another ROS 2 node's parameters** ([#4302](https://github.com/dora-rs/dora/pull/4302), [#4297](https://github.com/dora-rs/dora/issues/4297)). `Ros2Node.create_parameter_client("/robot/arm")` in Python, and `transport::parameters::ParameterClient` in Rust, wrap the target's six `rcl_interfaces` parameter services (`get`, `get_types`, `set`, `set_atomically`, `list`, `describe`) and report its changes from `/parameter_events`, on DDS and native Zenoh. Before, dora could only host parameters. Under CycloneDDS a dora-hosted node's parameters stay out of reach until [#4215](https://github.com/dora-rs/dora/issues/4215).
- **A YAML ROS 2 action server can let its handler accept or reject each goal** ([#4248](https://github.com/dora-rs/dora/pull/4248), [#4234](https://github.com/dora-rs/dora/issues/4234)). When the bridge node declares a `goal_response` input, the bridge forwards each new goal on `goal` without answering the ROS 2 client. It then accepts or rejects the goal as the handler answers on a `goal_response` input: the goal's `goal_id` in the metadata and a one-element boolean array, `true` to accept, as data. A goal without an answer within 10 s is rejected. Without that input the bridge keeps accepting every goal on arrival, and the `ros2:` config gains no new key. This works on DDS and native Zenoh.
- **`dora recording export` writes a `.drec` recording as MCAP** ([#3541](https://github.com/dora-rs/dora/pull/3541), [#3787](https://github.com/dora-rs/dora/pull/3787)). Every topic becomes an `arrow-ipc` channel, `--topics` picks a subset and `-o` names the output file. With `--format foxglove`, image outputs (declared as `std/media/v1/Image` or `std/media/v1/CompressedImage`, or carrying `width`/`height`/`encoding` metadata next to a flat `uint8` payload) are re-encoded as Foxglove's `RawImage`/`CompressedImage` so Foxglove can display them.
- **`dora recording diff OLD NEW` compares two recordings** ([#4010](https://github.com/dora-rs/dora/pull/4010)). It checks that each node output has the same number of messages with the same data, and exits 0 when they match, 1 when they differ and 2 on an error.
- **Generated C++ ROS 2 service and action clients and servers work on native Zenoh** ([#3771](https://github.com/dora-rs/dora/pull/3771), [#3991](https://github.com/dora-rs/dora/pull/3991)). They used to fail with "entity requires the DDS transport". The C++ signatures are unchanged.
- **Python ROS 2 nodes on native Zenoh support parameters and `rosout=True`** ([#3889](https://github.com/dora-rs/dora/pull/3889)). They serve the six `rcl_interfaces` parameter services and publish `/parameter_events`, like on DDS.
- **The ROS distro is a Cargo feature** ([#3560](https://github.com/dora-rs/dora/pull/3560)). `dora-ros2-bridge`, `dora-ros2-bridge-arrow`, the YAML bridge node, the Python bridge and the `dora-rs` wheel crate expose `ros2-humble`, `ros2-iron`, `ros2-jazzy` and `ros2-kilted`. Humble stays the default, and the newest enabled distro wins.
- **The DDS ROS 2 bridge diagnoses why it cannot talk to a ROS 2 peer** ([#4226](https://github.com/dora-rs/dora/pull/4226)). It names the QoS policy that keeps an offered and a requested endpoint from matching, and the `RMW_IMPLEMENTATION` to set when a Fast-DDS or CycloneDDS peer's service mapping does not fit.
- **`DORA_ROS2_DDS_INTERFACES` restricts the DDS participant to the listed local IPv4 addresses** ([#4228](https://github.com/dora-rs/dora/pull/4228)). RustDDS advertises every interface, including docker0, VPN and link-local ones, so a ROS 2 node on another host could send to one it cannot reach. Unset, nothing changes except one warning when more than one non-loopback address would be advertised.
- **The C++ node API exposes the extension seam** ([#3975](https://github.com/dora-rs/dora/pull/3975)): `extension_store`, `extension_load`, `extension_drop` and `drain_dropped_extension_keys`, with an example.
- **`Vec<bool>` and `Vec<String>` can be read back from a `DoraArray`** ([#3810](https://github.com/dora-rs/dora/pull/3810)). `Vec<String>` accepts `Utf8`, `LargeUtf8` and `Utf8View`.
- **Python `merge_external_events(subscription, id=None)` labels each merged stream** ([#3749](https://github.com/dora-rs/dora/pull/3749)). Its events carry the `id` you pass, or by default the subscription's topic name, as `event["id"]`, so one node can tell several ROS 2 subscriptions apart.
- **Tensor pool: a GPU frame from a peer machine is materialized in a pool the receiver owns** ([#3941](https://github.com/dora-rs/dora/pull/3941)). The tensor pool is opt-in and outside the 1.0 guarantees.

### Changed

- **A YAML ROS 2 service client keeps several requests in flight instead of one at a time** ([#4260](https://github.com/dora-rs/dora/pull/4260), [#4258](https://github.com/dora-rs/dora/issues/4258)). It used to send a request and block until the response came or 30 s passed before reading the next input, so one slow request held up every request behind it. Now it sends each request as its input arrives and keeps as many in flight as its service QoS history holds (`keep_last`, 10 by default, at most 64), and gives up on the oldest unanswered one once the server has answered nothing for 30 s since that request was sent, so a server that answers one at a time never makes queued requests time out, while one that stops answering fails them all about 30 s later. Responses still come out in request order. **The ROS 2 server now gets several requests at once; set `qos.keep_last: 1` to keep sending one at a time.** Each `response` also carries the metadata parameters of the request it answers, except delivery keys such as `flush`, so a dataflow can match them by an id it sets. On DDS and native Zenoh.

### Fixed

- **`dora record` and `dora replay` work after a normal install** ([#4304](https://github.com/dora-rs/dora/pull/4304), [#3800](https://github.com/dora-rs/dora/issues/3800)). Both need the `dora-record-node` and `dora-replay-node` helpers, which were not published, so the CLI's install fallback could never resolve them and the release archives shipped `dora` alone. The CLI release archives and the `install.sh`/`install.ps1` installers now ship both helpers next to `dora`, and both crates are published to crates.io. The CLI looks for them next to the `dora` executable, then in `~/.dora/nodes/<version>/bin`, then on `PATH`. If none is found outside the dora workspace, it installs the matching version from crates.io into `~/.dora/nodes/<version>`, which needs a Rust toolchain. **The `dora-rs-cli` wheel still ships the CLI alone, and a `dora self update` from 1.1 replaces only `dora`, so re-run the installer afterwards to get the helpers.**
- **A YAML ROS 2 action server forwards cancel requests to its handler when it declares a `cancel` output, and rejects them when it does not** ([#4238](https://github.com/dora-rs/dora/pull/4238), [#4234](https://github.com/dora-rs/dora/issues/4234)). On DDS the bridge never read cancel requests, so a client's cancel timed out and the goal ran to the end. On native Zenoh it accepted them and published `CANCELING` without telling the handler, so the goal still ended `SUCCEEDED`. With `outputs: [goal, cancel]` the bridge now answers the cancel, marks the goals `CANCELING` and sends one `cancel` event per goal, with its `goal_id`, to the handler. The handler ends a goal by sending `result` with `goal_status: canceled`. **Without a `cancel` output, every cancel request is now answered `ERROR_REJECTED` on both transports;** on Zenoh this replaces the misleading acceptance, so declare the output if a handler should act on cancels.
- **`dora down` on Windows no longer leaves a node's child processes running after the node's own process exits** ([#4109](https://github.com/dora-rs/dora/pull/4109)). On the `dora up` path a node's job object is not kill-on-close, so nodes survive a daemon restart, and the destroy wait only checked the node's main process. When a wrapper such as `cmd`, `uv` or a shell exited first, the destroy finished right away and the process it had started, for example `python.exe`, kept running. The daemon now also waits for the node's child processes and kills them when the destroy deadline passes.
- **`dora node add`/`remove`/`replace`/`connect`/`disconnect` no longer stall the coordinator while a daemon is slow to answer** ([#4061](https://github.com/dora-rs/dora/issues/4061)). The coordinator waited for the daemon's reply inside its serial event loop, for up to 30 s, so it sent no heartbeats meanwhile and could then disconnect healthy daemons. These changes now run one at a time per dataflow, off the event loop; one whose daemon disconnects fails at once, and one that gets no answer reports that its outcome is unknown instead of committing anything. A node's exit that is reported while its add, replace or remove is still in flight is applied after the change commits, and `dora restart` is refused while a node change is in progress, so neither can be lost to the new ordering.
- **A dataflow whose daemon finished it while disconnected from the coordinator now settles from the daemon's resent result** ([#3635](https://github.com/dora-rs/dora/pull/3635), [#3631](https://github.com/dora-rs/dora/issues/3631), [#4093](https://github.com/dora-rs/dora/pull/4093)). If the coordinator handled a daemon's disconnect before that daemon's finish report, the dataflow was left `Recovering` and the report the daemon resent after reconnecting was dropped. 60 s later the dataflow was marked `Failed` with "recovery timeout (60s): no daemon reconnected" and no node results. The resent report is now accepted, and once every daemon of the dataflow has reported, the dataflow is marked `Succeeded` or `Failed` from the node results. While such a multi-daemon dataflow waits for a daemon to come back, `dora list` no longer shows it Finished and `dora stop` no longer reports success without stopping it.
- **`dora-cli` builds again with `--no-default-features`** ([#4071](https://github.com/dora-rs/dora/issues/4071)). Without the `tracing` feature the coordinator subcommand passed `()` where `start_with_auth` expects an `Option` span store, and `libc`, used unconditionally by `dora daemon --rt` on Unix, was only a dependency of the `redb-backend` feature. The span store is now `None`, `libc` is a plain Unix dependency, and imports used only with `tracing` are gated on it.
- **`dora start` no longer detaches from a dataflow it just started when a Python operator's source is a URL or exists only on the deploy target** ([#4049](https://github.com/dora-rs/dora/pull/4049)). The attach step looked up every Python operator's file for hot-reload, even without `--hot-reload`, and exited with "failed to resolve node source" when it found none. The dataflow kept running with no logs, and Ctrl-C could not stop it. Sources are now looked up only with `--hot-reload`, in the node's working directory (honouring `deploy.working_dir`), and a source that can't be watched there gets a warning instead of ending the attach.
- **The published dataflow schema describes an input as the string it is** ([#3701](https://github.com/dora-rs/dora/issues/3701), [#3713](https://github.com/dora-rs/dora/pull/3713), [#4060](https://github.com/dora-rs/dora/pull/4060)). `dora-schema.json` described `inputs` values only as `Timer`/`Logs`/`User` objects, which dora never accepted, so editors using the schema flagged every input as invalid. An input is now a string containing a `/` (`<source>/<output>`, `dora/timer/...` or `dora/logs...`), and the object forms are gone from the schema.
- **A log reader that cannot keep up no longer paces the whole coordinator** ([#3794](https://github.com/dora-rs/dora/issues/3794)). The coordinator's event loop waited up to 100 ms on each log subscriber for every log line, and a reader that freed a slot now and then was never evicted. A `dora logs -f` / `dora start --attach` on a link slower than the log rate, or a WebSocket client that reads slowly, therefore throttled daemon events and control requests indefinitely. (The dora CLI reads the socket on its own thread, so a slow terminal or a paused pager does not cause this.) Live log lines are now queued without waiting, in a per-connection queue capped at 16 MiB. Lines past the cap are dropped, and the reader gets a `dropped N log line(s)` notice right before the next line, which `dora logs -f` shows even with a node or `--grep` filter. The backlog replayed when a reader attaches, and the coordinator's own status lines such as "dataflow finished", are never dropped.
- **A held `backpressure` message survives its producer exiting, and is never delivered after its input's `InputClosed`** ([#3623](https://github.com/dora-rs/dora/pull/3623), [#3619](https://github.com/dora-rs/dora/issues/3619)). Since #3590 a message for a full receiver is held while the producer's `send_output` returns. If the producer then exited, the receiver could get `InputClosed`, and even `AllInputsClosed`, before the held `Input`, and the node API dropped that message without it being counted. The receiver's `InputClosed` and `AllInputsClosed` now wait until the held message is in, or dropped and counted under the 60 s rule. The finish drain clock and its straggler watchdog start when `AllInputsClosed` is actually sent. An `input_timeout` no longer fires on an input while a message for it is held.
- **`dora record` no longer fails on, or leaks the values of, `$VAR` references in the dataflow file** ([#3681](https://github.com/dora-rs/dora/pull/3681)). The original descriptor reached the record node as an `env:` value, which is `$VAR`-expanded every time it is parsed. A `$NAME` anywhere in the file, even in a comment, failed `dora record` with "data did not match any variant of untagged enum EnvValue" when `NAME` was unset, and was substituted when it was set, so for example the value of `${API_TOKEN}` ended up in plain text in the `.drec` header. The descriptor is now passed compressed and base64-encoded as `DORA_RECORD_DESCRIPTOR_DEFLATE_BASE64`. `dora record` keeps setting the raw `DORA_RECORD_DESCRIPTOR` when the file contains no `$` and the result still fits, so a `dora-record-node` from 1.0.x still records the descriptor; **for a file that contains `$`, rebuild `dora-record-node` together with the CLI**, otherwise the older node writes an empty descriptor and `dora replay` cannot use the recording. On Linux, `dora record` now refuses a dataflow whose descriptor, with the record node added, is over 128 KiB, the limit for the single environment variable the daemon passes it to every node in; before, every node failed to spawn with `E2BIG`.
- **A multi-daemon dataflow fails its spawn at once when one of its daemons disconnects during the spawn** ([#4047](https://github.com/dora-rs/dora/pull/4047), [#3736](https://github.com/dora-rs/dora/issues/3736)). Before, the coordinator only removed the lost daemon from the dataflow and left the rest to the order of the surviving daemons' reports: depending on that order, the dataflow could show as running while its nodes waited forever for the start barrier, run without the lost daemon's nodes, or have its nodes started and then force-stopped by the 60 s spawn timeout. The spawn now fails right away with an error naming the daemon, and the surviving daemons are told to stop the dataflow. **A daemon whose connection drops even briefly while a spawn is pending now fails that spawn for good**; before, the spawn could still complete if the daemon came back in time.
- **A ROS2 message the bridge cannot serialize is dropped, not fatal to the bridge node** ([#3795](https://github.com/dora-rs/dora/issues/3795)). Since #3678 a null nested-message, sequence or array row fails to serialize, and every bridge path returned that error and exited, taking all other topics, services and actions of the node down with it. The bridge now logs a warning and drops that one message: a topic publish skips it, a service or action client skips that call, a Zenoh service server rejects the request, and a Zenoh action server ends the goal as Aborted with a default result. Only a broken DDS participant (`Poisoned`, `Internal`) still ends the node.
- **Native Zenoh action servers in the YAML and Python bridges answer cancel requests the way rcl does** ([#4094](https://github.com/dora-rs/dora/pull/4094), [#3996](https://github.com/dora-rs/dora/issues/3996)). A cancel-all with no goal running is answered `ERROR_NONE` instead of `ERROR_UNKNOWN_GOAL_ID`, naming a goal that is already canceling or finished is answered `ERROR_GOAL_TERMINATED`, and a request with a non-zero stamp cancels the goals accepted at or before it. The Python server also sends the real acceptance stamp in its `SendGoal` reply and shows canceling goals as `CANCELING` in the status topic. **On Zenoh, Python `Ros2ActionServer.take_cancel()` now returns only the goals a request newly moved to canceling;** a repeated cancel of the same goal returns `[]`. DDS and the generated C++ server are unchanged.
- **A Zenoh ROS 2 service or action wait that times out no longer leaves its graph notification queued** ([#4089](https://github.com/dora-rs/dora/pull/4089), [#4078](https://github.com/dora-rs/dora/issues/4078)). `GraphCache::wait_for_change` kept the sender of every wait whose caller gave up until the ROS graph changed, so retrying for a server that never appears grew the list without bound. Waits whose receiver is gone are now dropped when the next one is registered.
- **A `KEEP_LAST` subscription on the native Zenoh transport keeps the newest samples, at most `depth` of them** ([#3861](https://github.com/dora-rs/dora/pull/3861), [#3817](https://github.com/dora-rs/dora/issues/3817)). A full subscription queue dropped the incoming sample whatever the QoS, and the queue held a fixed 64 samples (32 in generated C++) regardless of the history depth, so a slow reader got stale data. A `KEEP_LAST` subscription now holds at most `depth` unread samples and drops the oldest when full, as rmw_zenoh and the DDS transport do. `KEEP_ALL` is unchanged. **The default depth is 1** (`keep_last` in a `ros2:` node, `Ros2QosPolicies` in Python), so a reader on Zenoh that relied on the old 64-sample buffer to ride out bursts now sees only the latest sample; set `keep_last` to the depth it needs, or use `keep_all`.
- **An `env:` value is `$VAR`-expanded once, by the CLI, and not again on the coordinator or daemon** ([#3947](https://github.com/dora-rs/dora/issues/3947), [#4039](https://github.com/dora-rs/dora/pull/4039), [#4067](https://github.com/dora-rs/dora/issues/4067)). The descriptor's env strings were expanded every time it was decoded, so a value whose expansion contained `$` was expanded again against the receiving host's environment. `DB_PASSWORD: ${DB_PASSWORD}` with a password such as `p$ssw0rd` failed the coordinator's decode or reached the node changed, and a CLI variable holding `${DORA_AUTH_TOKEN}` handed the node the coordinator's or daemon's token. A string is now encoded with each `$` written as `$$`, which the next decode turns back into `$`, so the value the CLI expanded reaches the node unchanged. Module `params:` injected as `PARAM_<KEY>` are now expanded when the module is expanded, against the CLI's environment rather than the coordinator's. **Upgrade note: `$$VAR` in a YAML `env:` value used to be expanded on the coordinator host, and now reaches the node as the literal text `$VAR`.** `dora expand`, which prints the descriptor in the form dora itself re-reads, shows a `$` in an env string as `$$`, the form that parses back to the same value. Python `node.dataflow_descriptor()`, a Python operator's `self.dataflow_descriptor` and C++ `dataflow_descriptor_json` show the value itself. A coordinator from an earlier release still expands the value once more when it forwards it to the daemon, so `dora start --env` / `dora run --env` keep refusing `$`.
- **The ROS2 bridge rejects a null sequence, array or message instead of publishing invented values** ([#3678](https://github.com/dora-rs/dora/pull/3678)). Null scalars, strings and sequence elements were already rejected, but a null row of a `T[]`, `T[N]` or nested-message field, and a null element of an `Inner[]` sequence, went out as whatever the row's masked buffers held: an empty sequence, stale values, or an all-zero message rather than the ROS default. They are now errors. **Python nodes that pass `None` to mean "empty" or "default" must change:** send `[]` for an empty sequence, and omit a field entirely to get its ROS default.
- **A synchronous event loop inside a tokio task no longer stalls after 128 events** ([#3673](https://github.com/dora-rs/dora/issues/3673)). `EventStream::recv`, `recv_timeout` and `try_recv` drive tokio's channel receiver from synchronous code, so they spent the calling task's coop budget without ever yielding to refill it. In a task that never yields, for example a plain `while let Some(event) = events.recv()` loop in `#[tokio::main]`, the receiver reported nothing ready after 128 receives with events still queued: `recv` spun forever, `recv_timeout` timed out and `try_recv` returned `Empty`. The three methods now run the receive outside the budget. Async receives (`recv_async`, the `Stream` impl) still take part in it.
- **`dora start --hot-reload` reports a reload the node never received** ([#3215](https://github.com/dora-rs/dora/pull/3215), [#4131](https://github.com/dora-rs/dora/pull/4131)). A reload was reported as successful when the node's event channel was full or closed, or when the node had not subscribed to its events yet. The daemon now returns an error that names the node, and the attached CLI logs it as a failed reload with the reason.
- **`path: shell` nodes on Windows keep the double quotes in their `args`** ([#4073](https://github.com/dora-rs/dora/issues/4073)). The daemon ran the script as `cmd /C <script>` with the script as an ordinary argument, so Rust escaped every `"` as `\"`, which `cmd.exe` does not understand: `echo "a b"` printed `\"a b\"` and `python -c "print('hi')"` failed with a syntax error. The script is now handed to `cmd /S /C "<script>"` verbatim, so a script that itself starts with a quote works as well. Linux and macOS are unchanged.
- **A quoted `env:` value that looks like a number reaches the node exactly as written** ([#3703](https://github.com/dora-rs/dora/pull/3703)). `VERSION: "1.10"` reached the node as `1.1`, `"007"` as `7` and `"1e3"` as `1000`, and the same happened to `$VAR` references that expanded to such text. A string is now typed as a bool or number only when the typed value prints back as the same text, so `"8080"`, `"true"` and `${PORT}` keep the `Integer`/`Bool` type they always had in `dataflow_descriptor()`, and only values that used to be rewritten stay strings. A dataflow with such a value rebuilds once after upgrading, because its build fingerprint hashes the corrected text. Coordinators and daemons from earlier releases still coerce these values, so `dora start --env` / `dora run --env` keep refusing them.
- **`dora self update` from 1.0 and 1.1 finds the CLI archive** ([#4034](https://github.com/dora-rs/dora/issues/4034), [#4133](https://github.com/dora-rs/dora/pull/4133)). Those CLIs take the first release asset whose name contains their target, and `dora-c-libraries-<target>` sorted before `dora-cli-<target>`, so they downloaded the C libraries and failed. The C and C++ archives are renamed so the CLI comes first on Linux and macOS. **Upgrade note: the release assets `dora-c-libraries-<target>.*` and `dora-cpp-libraries-<target>.*` are now `dora-libraries-c-<target>.*` and `dora-libraries-cpp-<target>.*`, and so are the directories inside them;** update scripts or CMake paths that use the old names. On Windows, 1.0 and 1.1 still can't extract the Deflate-compressed CLI zip, so reinstall once with the installer.
- **A relative topic name on the native Zenoh transport is now put under the node's namespace** ([#3992](https://github.com/dora-rs/dora/pull/3992), [#3977](https://github.com/dora-rs/dora/issues/3977)). A relative name such as `chatter` was used as is, so a node in `/robot1` published and subscribed on `chatter` at the root instead of `/robot1/chatter` as DDS and rcl do, and nodes in different namespaces that both used `chatter` shared one topic. Generated C++ topics and Python `create_topic` on Zenoh now resolve a relative name to `<namespace>/<name>`, and to `/chatter` under the root namespace. DDS, Python services and actions, and the YAML `ros2:` bridge are unchanged. **A peer that relied on the old root-level name must change:** after upgrading it receives nothing and no error is reported, so move the peer to the namespaced name, or give the topic an absolute name such as `/chatter` on the dora side to keep the old key.
- **The tensor-pool direct-TCP data listener caps its connections and drops silent ones after 10 s** ([#4059](https://github.com/dora-rs/dora/pull/4059), [#4033](https://github.com/dora-rs/dora/issues/4033)). The mirror's listener (`DORA_MEMORY_POOL_DATA_PORT`, default `0.0.0.0:7410`) served every connection it accepted, and a connection could sit silent for 300 s before the auth handshake or first frame timed out, so any host that could reach the port could exhaust the daemon's file descriptors and break unrelated daemon work. It now serves at most `DORA_MEMORY_POOL_MAX_DATA_CONNECTIONS` connections at once (default 256) and closes the rest, and a fresh connection must finish the auth handshake and start its first frame within 10 s each, with or without a token. While the cap is exhausted, direct writes fail rather than degrade: with a token the origin falls back to the zenoh relay, without one the write can be lost and fail on its ack timeout.

#### Other fixes

Dataflow lifecycle and daemon:

- Node liveness timers (health check, startup timeout, finish stragglers) run on a monotonic clock, so a forward NTP step no longer makes the health check kill every node and a backward one no longer disables the watchdogs ([#4231](https://github.com/dora-rs/dora/pull/4231)). The wait at the startup barrier no longer counts as health-check silence ([#4200](https://github.com/dora-rs/dora/pull/4200)).
- A restarted node gets its runtime parameters back ([#4142](https://github.com/dora-rs/dora/pull/4142)), and a node in restart backoff is reported as Restarting from its first crash ([#4222](https://github.com/dora-rs/dora/pull/4222)).
- `dora top` no longer shows an exited node's recycled PID as Running ([#4197](https://github.com/dora-rs/dora/pull/4197), [#4273](https://github.com/dora-rs/dora/pull/4273)), keeps each daemon's network counters in a multi-daemon dataflow ([#3980](https://github.com/dora-rs/dora/pull/3980)), and its process walk no longer loops on a pid cycle on Windows ([#4032](https://github.com/dora-rs/dora/pull/4032)). A metrics cycle is skipped while the previous one still runs ([#3811](https://github.com/dora-rs/dora/pull/3811)).
- Node IPC listeners stay off Zenoh ports planned by their own or another dataflow on the same daemon ([#4184](https://github.com/dora-rs/dora/pull/4184), [#4247](https://github.com/dora-rs/dora/pull/4247)).
- `dora node remove` forgets that a node was dynamic ([#4275](https://github.com/dora-rs/dora/pull/4275)), and a static node in one dataflow no longer blocks a same-named dynamic node from joining another ([#3880](https://github.com/dora-rs/dora/pull/3880)).
- A node that sends a request this daemon cannot decode gets an error instead of hanging ([#3807](https://github.com/dora-rs/dora/pull/3807)), and an undecodable `SendMessage`/`OutputSent` frame gets no stray reply ([#4117](https://github.com/dora-rs/dora/pull/4117)). - A producer that exits right after a burst to a remote consumer no longer leaves the consumer's input open until `dora stop`: the daemon's `OutputClosed` to other machines is no longer dropped on a full publish queue ([#4268](https://github.com/dora-rs/dora/pull/4268)).
- A stop succeeds for a dataflow that just finished on that daemon ([#3903](https://github.com/dora-rs/dora/pull/3903)). A daemon reconnecting with a pending start barrier reports it under its new id ([#4190](https://github.com/dora-rs/dora/pull/4190)).
- A `dora/logs` subscriber that crashes stays subscribed after its restart ([#3757](https://github.com/dora-rs/dora/pull/3757)), and a backpressure receiver that gave up stays marked until it has drained ([#3634](https://github.com/dora-rs/dora/pull/3634)).
- The daemon's main loop no longer deadlocks on its own full channel when a node stops ([#3743](https://github.com/dora-rs/dora/pull/3743)), and a node listener backs off on `EMFILE` instead of spinning ([#3879](https://github.com/dora-rs/dora/pull/3879)).

- Missing-link diagnostics name the zenoh ids and the routers a daemon is linked to ([#3952](https://github.com/dora-rs/dora/pull/3952), [#3955](https://github.com/dora-rs/dora/pull/3955)).

## v1.1.0 (2026-10-07)

### Breaking

- **`DoraEventType` has a new `NodeRestarted` variant** ([#3046](https://github.com/dora-rs/dora/issues/3046)). A restart of an upstream node reached C++ as `Unknown`, so a node could not reset state, resend work it had in flight, or even tell that anything had happened. It now arrives as `DoraEventType::NodeRestarted`, with `event_as_node_restarted(event)` returning the restarted node's id. This changes what existing C++ nodes see: a `switch` over `DoraEventType` without a `default` arm stops compiling under `-Werror=switch`. Add a `default`, or handle the new variant.

### Upgrade notes

These fixes reject input that 1.0.1 accepted or change how a running dataflow behaves. Each one replaces a crash, a hang, or silent data loss, but check them before upgrading.

- **Timing fields are validated on every start path** ([#3649](https://github.com/dora-rs/dora/pull/3649), [#3666](https://github.com/dora-rs/dora/pull/3666)). Only `dora run` rejected a negative, non-finite or overflowing `input_timeout`, `restart_delay`, `health_check_timeout` or other seconds-valued field. On `dora start`, `dora restart` and `dora node add`/`replace` the value reached the daemon and panicked it, taking down every dataflow on that daemon. These paths now reject the descriptor before any node spawns, and the daemon checks again so an older coordinator cannot crash it. An interval that rounds to zero nanoseconds, such as `health_check_interval: 1e-10`, is now rejected too ([#3345](https://github.com/dora-rs/dora/pull/3345)); it used to be accepted and silently replaced by the 5 s default.
- **`send_stdout_as` and `send_logs_as` must name a valid output id** ([#3643](https://github.com/dora-rs/dora/pull/3643)). Values such as `"std out"`, `out/` or `a//b` passed `dora validate`, then killed the node's log task at its first stdout line, so every later line of that node was lost. They are now rejected at validation and spawn time.
- **A git commit hash must be 4 to 64 hex digits** ([#3647](https://github.com/dora-rs/dora/pull/3647)). The hash, whether from a descriptor `rev:` or from the lockfile under `--locked`, becomes a path component in the clone cache, so a value such as `../../home/u/project` reached outside it.
- **ROS 2 bridge port mappings are checked against the node's declared ports** ([#3310](https://github.com/dora-rs/dora/pull/3310), [#3486](https://github.com/dora-rs/dora/pull/3486)). A `topics:` entry whose explicit or derived `output`/`input` is not declared on the node is now rejected by `dora validate`, `dora run` and `dora start`. Before, the bridge started and silently dropped every message for that topic. A single-topic bridge now binds to the declared port.
- **`dora replay --speed` is validated** ([#3381](https://github.com/dora-rs/dora/pull/3381)). Negative values, `nan`, `-inf` and values between 0 and `1e-6` are rejected. `0` and `inf` still mean "as fast as possible".
- **`dora record` rejects topics that collide under its input-id encoding** ([#3444](https://github.com/dora-rs/dora/pull/3444)). `x/y___z` and `x___y/z` both encode to `x___y___z`, and one of them used to be dropped from the recording without an error.
- **A full `backpressure` receiver now holds its producer instead of dropping messages** ([#3590](https://github.com/dora-rs/dora/pull/3590), [#3610](https://github.com/dora-rs/dora/pull/3610)). On the daemon path, a message for a `queue_policy: backpressure` input whose receiver channel is full waits for room, and the producer's next `send_output` blocks until it is delivered. Only that producer stalls; the daemon loop does not wait. A producer that used to run ahead of a slow backpressure consumer is now throttled to the consumer's pace. If the receiver frees no room for 60 s, the held message is dropped and counted, and the receiver's messages keep being dropped until it reads an event again. `dora replay` now fails when it loses a backpressure message, which makes `--speed 0` lossless.
- **`decode_arrow_ipc` rejects a stream with more than one record batch or with trailing bytes** ([#3588](https://github.com/dora-rs/dora/pull/3588)). It used to return the first batch and silently discard the rest.
- **The coordinator's WebSocket connection cap now applies for a socket's whole lifetime** ([#3600](https://github.com/dora-rs/dora/pull/3600)). The limit used to be released once the upgrade response was sent, so open connections were unbounded. CLI and daemon connections now have separate budgets, so a flood of CLI connections cannot lock out daemons. TCP keepalive frees the slot of a peer that disappears without closing the connection.
- `dora new` rejects some project names it used to accept, and `drain_drop_counts()` can report more drops than in 1.0.x. Both are described under Fixed.

### Added

- **Node startup watchdog via `startup_timeout`** ([#3360](https://github.com/dora-rs/dora/pull/3360)). Set the optional YAML field to bound how long a spawned node may take to connect. A node that exceeds the limit is killed and handled according to its restart policy; checks run at the configured `health_check_interval`.
- **Thread-safe output sending from C++ worker threads** ([#2288](https://github.com/dora-rs/dora/pull/2288)). `clone_output_sender()` creates a `SafeOutputSender`, and `safe_send_output()` sends raw bytes from worker threads while serializing access with the main thread's sender.
- **Rust `IntoArrow` conversion for `Vec<bool>`** ([#3445](https://github.com/dora-rs/dora/pull/3445)). Boolean vectors can be converted directly into Arrow boolean arrays.
- **Expanded Python `MockNode` testing support** ([#3516](https://github.com/dora-rs/dora/pull/3516)). Adds configuration getters, structured-log capture, queue inspection, and service request/reply simulation for node unit tests.
- **`dora record --queue-size`** ([#3282](https://github.com/dora-rs/dora/issues/3282)). Sets the `queue_size` of every topic the recorder subscribes to, default 100 — roughly one flush window of slack per topic. Raise it to ride out longer write stalls; peak memory is about `2 x queue_size x payload size` per topic. Rejected together with `--proxy`, which does not route through those queues.

### Fixed

- **Two daemons on one machine no longer depend on multicast to find each other.** A daemon whose coordinator is on loopback bound a loopback zenoh listener but did not report it, so a second daemon on the same host (`dora up` plus a `dora daemon --machine-id`, or the `multiple-daemons` example) only found it through zenoh multicast scouting. Where that is unavailable or slow — dev containers, some CI runners — the two daemons never linked, nothing crossed between them (not even the "outputs closed" that lets a consumer finish), and the dataflow hung without any message. Loopback listeners are now reported too, and the coordinator hands them only to daemons that reached it over loopback themselves, so a daemon on another machine is still never pointed at its own loopback. Loopback listeners use a separate wire field that 1.0.x coordinators ignore, so daemons and the coordinator can be upgraded in either order; same-host discovery continues to rely on multicast until the coordinator is upgraded. Independently, once every daemon of a dataflow has spawned, a daemon now checks that the others answer its zenoh node-endpoint query: if one does not, it warns, keeps probing for 30 s, and logs either that the link formed late or an error naming the unreachable daemons and what to check.
- **A `queue_policy: backpressure` input is no longer discarded by a timer flood** ([#3428](https://github.com/dora-rs/dora/issues/3428)). The direct node-to-node zenoh path hands each message to the receiver with a non-blocking send into one ingress channel shared by all of the receiver's inputs, so a fast timer could fill that channel while the receiver was busy and the next backpressure message was dropped before the per-input policy saw it. Any output with a `backpressure` consumer now stays on the daemon path, whose delivery into that channel blocks instead of dropping. This costs the whole output its zero-copy path and puts it under the daemon's 64 MiB per-message limit; the daemon path remains a bounded buffer, not a guarantee (see `docs/yaml-spec.md`). `dora node add`/`replace` now refuse a `backpressure` input whose producer is already running with the output on the direct path, since a running producer cannot be re-routed. `dora replay` marks every unset input `backpressure`, so replay dataflows run on the daemon path.
- **A node that stalls and then asks for events no longer loses its whole backlog.** The daemon answered the next-event request with every queued event in one frame; past 64 MiB the frame was refused and the events, already dequeued, were dropped with only a warning while `dora run` still exited 0. Replies are now cut by exact wire length so each fits the 64 MiB frame, metadata included, and the remainder waits for the next request; an event that alone cannot fit is dropped with an error instead of wedging the queue.
- **A consumer that stops reading can no longer grow daemon memory without bound.** The per-node listener drained the receiver's bounded channel into an unbounded queue. The queue is now capped at 1000 events or 256 MiB of payload; past that the channel fills and the existing sender-side drop policy applies.
- **`dora new` no longer scaffolds a project that cannot build from an invalid name** ([#3440](https://github.com/dora-rs/dora/issues/3440)). The name argument was substituted unescaped into the generated `CMakeLists.txt` (`project(___name___ …)`), `Cargo.toml`, and `pyproject.toml` (`name = "___name___"`), and used as a directory name, but validation only rejected `/` and non-ASCII. So `dora new --lang c --kind node "my node"` emitted a `project(my node …)` CMake fails to configure, and `dora new --lang rust --kind node 'foo"bar'` emitted invalid TOML — in each case the error pointed at a generated file the user never wrote. All four backends now share one allow-list — ASCII letters, digits, `-`, `_` (plus spaces on the Python node path, which normalizes them before use) — so every name that passes validation is safe in all of those contexts. **One narrowing to note:** a PEP 508 project name may contain `.`, so `dora new --lang python --kind node my.node` was accepted before and is now rejected. Names with `.` (and the other newly-rejected punctuation) already produced a `Cargo.toml`/`pyproject.toml` the toolchain refuses on every other backend, so this trades a confusing downstream failure for an immediate, clear one.
- **`dora new` also rejects the remaining names that pass the character allow-list but still break the build** ([#3440](https://github.com/dora-rs/dora/issues/3440)). A name must now start with an ASCII letter and end with a letter or digit, and cannot be one of `build`, `deps`, `examples`, or `incremental`. A leading digit (`2048`) is an invalid Python module name, a trailing `-`/`_` (`foo-`) is an invalid PEP 508 project name, and the four reserved names collide with cargo's build-directory names when used as the Rust node's implicit binary target.
- **Dataflow entrypoints referenced via symlinks resolve the project root consistently** ([#3247](https://github.com/dora-rs/dora/issues/3247), [#3465](https://github.com/dora-rs/dora/pull/3465)). Previously, canonicalizing the dataflow file resolved symlinks in the file itself to their physical target, causing `dora build`, `dora run`, and the daemon to treat the target directory as the project root. Project root resolution now canonicalizes the lexical parent directory of the entrypoint path, ensuring that relative module paths, node paths, and build workspaces resolve against the entrypoint's containing directory.
- **`dora record` no longer ends up silently short** ([#3282](https://github.com/dora-rs/dora/issues/3282)). The hidden `__dora_record__` node wrote its subscriptions as bare `node/output` strings, which take dora's real-time defaults — a 10-deep queue with `drop_oldest`. That is the wrong shape for a node whose work is disk I/O: a producer burst or a stalled write evicted the oldest events before the writer saw them, and the `.drec` contained nothing to say so. Each input now carries an explicit `queue_size` (see `--queue-size` above), and the run ends with a per-topic report of what was lost instead of a bare message count. Depth alone cannot make recording lossless — a producer declares its publisher with `CongestionControl::Drop` at declare time, shared by every subscriber, so no lossless path is available to an observer that does not perturb the dataflow it is recording. The fix widens the window and reports the residue rather than promising zero loss.
- **`drain_drop_counts()` no longer reports zero while a node is losing zero-copy messages** ([#3282](https://github.com/dora-rs/dora/issues/3282)). A payload on the direct node-to-node zenoh path is handed to the receiver by a `try_send` into one ingress channel shared by all of that node's inputs, and a full channel drops it there — before the scheduler, and so before the per-input queues whose counters this function returned. That site only logged, so the one programmatic way a node can learn it lost data read zero while every message it could not keep up with was being discarded. Both loss sites are now counted per input. **The returned numbers can therefore be larger than before** for a node on the direct path: a node that does its own drop accounting will see counts it did not see in 1.0.x. The ingress channel is sized from the sum of the node's input `queue_size`s (floor 64), so raising any input's `queue_size` also deepens it.

- `dora restart` relaunches the dataflow with its original working directory, session, build and `write_events_to`. A relative node `path:` from a local `dora start` used to stop resolving after a restart, and built nodes lost their build ([#3677](https://github.com/dora-rs/dora/pull/3677)).
- A hard-killed `dora run` no longer leaves nodes running: on Linux the kernel kills nodes that have not reached `init` yet ([#3482](https://github.com/dora-rs/dora/pull/3482)), and on Windows the node tree is killed when the job closes ([#3544](https://github.com/dora-rs/dora/pull/3544)).

- A node TCP connection whose framing is lost (oversized length header, a body that stalled past the read timeout) is dropped instead of read as garbage while the node waits forever for its reply ([#3624](https://github.com/dora-rs/dora/pull/3624)).
- A coordinator no longer disconnects a live daemon on a heartbeat-send backpressure timeout ([#2886](https://github.com/dora-rs/dora/pull/2886)), and sends a reconnecting daemon only the catch-up entries for its own nodes ([#3692](https://github.com/dora-rs/dora/pull/3692)).

- A huge `restart_delay` saturates the restart backoff instead of panicking the daemon ([#3614](https://github.com/dora-rs/dora/pull/3614)).
- The daemon counts a message that finds the receiver's channel closed ([#3622](https://github.com/dora-rs/dora/pull/3622)), drops a removed node's cached remote publishers ([#3351](https://github.com/dora-rs/dora/pull/3351)), answers unsupported requests on the local listener ([#3285](https://github.com/dora-rs/dora/pull/3285)), and logs an extension-request handler error instead of propagating it ([#3382](https://github.com/dora-rs/dora/pull/3382)).

- `dora top` no longer counts node threads as processes ([#3559](https://github.com/dora-rs/dora/pull/3559)).

## v1.0.1 (2026-09-03)

Patch release. 1.0.0 could not be installed from crates.io.

### Fixed

## v1.0.0 (2026-09-02)

### Breaking

- **A module node may no longer carry source fields.** `module:` together with any of `path`, `args`, `path_sha256`, `git`, `hub`, `branch`, `tag`, `rev`, `operators`, `operator`, or `ros2` is now rejected at expansion time. These combinations parsed and ran before: the extra fields were accepted and then silently discarded when the module node was replaced by its expansion, so a `module:` node with a `path:` ran the module and ignored the path with no diagnostic. The rejection reaches `dora run`, `dora start`, `dora build`, `dora validate`, and `dora expand --module`. `env`, `build`, `deploy`, and `params` are unaffected — they propagate into the module's inner nodes. Remove the offending fields, or drop `module:` if the node was meant to be a regular node.
- **The `_unstable_` prefix is dropped from the `deploy` and `debug` descriptor keys** ([#3220](https://github.com/dora-rs/dora/pull/3220)). `_unstable_deploy:` becomes `deploy:` and `_unstable_debug:` becomes `debug:`. `Node` is `#[serde(deny_unknown_fields)]`, so a descriptor still using the prefixed keys is rejected at parse time rather than silently ignored. Rename the keys; the values are unchanged.
- **Arrow is no longer part of the frozen `dora-node-api` public API** ([#3213](https://github.com/dora-rs/dora/pull/3213)). Arrow types reached the API surface through re-exports, which would have pinned the 1.0 compatibility promise to an Arrow major version. Depend on `arrow` directly for the types you need.
- **The `dora_core` re-export is narrowed out of the 1.0 surface** ([#3221](https://github.com/dora-rs/dora/pull/3221)). `dora-core` is an internal crate; re-exporting it wholesale committed 1.0 to its internals. Code reaching through the re-export must depend on the specific types it uses.
- **The tensor-pool cross-machine transport moves back behind the extension seam** ([#3219](https://github.com/dora-rs/dora/pull/3219)). It is opt-in and outside the 1.0 stability guarantees; see `libraries/extensions/tensor-pool/README.md`.
- **The deprecated descriptor surface is removed** ([#3158](https://github.com/dora-rs/dora/pull/3158)). Fields and forms that carried a deprecation warning are now hard errors. `deny_unknown_fields` means these fail loudly at parse time.
- **The wire-protocol enums are `#[non_exhaustive]`** ([#3151](https://github.com/dora-rs/dora/pull/3151)). Adding a variant is no longer a breaking change, so downstream `match` expressions on `dora-message` enums need a wildcard arm.
- **The descriptor structs are `#[non_exhaustive]`** ([#3387](https://github.com/dora-rs/dora/pull/3387)). `Descriptor`, `Node`, `CustomNode`, `ResolvedNode`, `OperatorConfig`, `SingleOperatorDefinition`, `Deploy`, `Debug` and `TypeRuleDef` can no longer be built with a struct literal outside `dora-message`. Construct through `Node::new(id)`, `CustomNode::new(path)`, `Descriptor::new(nodes)`, `ResolvedNode::new(id, kind)`, `TypeRuleDef::new(from, to)` or `Default` (`Deploy`, `Debug`) and assign the fields you need — they stay `pub`. No YAML or wire-format change.

- **Binary wire format moved from bincode to postcard.** [bincode is unmaintained](https://rustsec.org/advisories/RUSTSEC-2025-0141.html) — development stopped at 1.3.3 and all versions are flagged — so it is not something to carry into 1.0. Every binary plane moves to [postcard](https://docs.rs/postcard), which is serde-based (so the migration is encoding-only, no type changes), actively maintained, and unlike bincode has a **documented, stable wire spec** — the right property for a format 1.0 commits to. Messages shrink 25–27 bytes each (`Metadata` alone: 34 → 27 B) because postcard varint-encodes integers and length prefixes; serialization speed is at parity or slightly better once the encode buffer is pre-sized (`dora_message::to_vec_with_capacity`), and deserialization is unchanged to slightly faster. The JSON planes (CLI ↔ coordinator, coordinator ↔ daemon WebSocket) are untouched. This breaks four things, all of which fail loudly:
  - **Mixed-version deployments.** `Metadata::CURRENT_VERSION` is bumped `1` → `2`, so a node and daemon that both speak postcard but disagree on layout are rejected at register with a clear version-mismatch error. A peer from *before* this change (v1.0.0-rc.4 or earlier) speaks bincode, so its register frame fails to decode before that check runs: the daemon logs the deserialization error and drops the connection, and the node sees a register timeout rather than a version message. The `dora_version` semver gate does not catch it either — `VersionReq::parse("1.0.0-rc.4")` yields `^1.0.0-rc.4`, which matches `1.0.0`. **Upgrade daemon and nodes together; do not mix rc builds with 1.0.0.**
  - **Coordinator persisted store: `SCHEMA_VERSION` bumped `4` → `5`.** Stored records are postcard-encoded now, and postcard is positional rather than self-describing, so v4 rows cannot be read. `RedbStore::open()` rejects a v4-stamped database with a `schema version mismatch` error. **If you have an existing coordinator store** (`~/.dora/` by default; `redb` is the default `--store` backend), `dora coordinator` will refuse to start after upgrading. Delete the store file (its path is named in the error message) to start fresh, or pass `--store memory` to bypass persistence.
  - **`.drec` recordings: format version bumped `1` → `2`.** Entry payloads are postcard-encoded. The container framing is unchanged, so a v1 file would otherwise pass the header check and then fail per-entry; the reader now rejects it up front, naming the cause. Re-record with this release — there is no converter.
  - **The WebSocket topic-data channel** (`docs/websocket-topic-data-channel.md`) carries raw `Timestamped<InterDaemonEvent>` bytes, now postcard. Both encodings are positional, so a bincode-era third-party subscriber would *misparse* rather than error. The subscription handshake now carries `protocol_version` in both directions (`dora_message::TOPIC_DATA_PROTOCOL_VERSION`, currently `2`) and either side refuses the subscription on mismatch, so this surfaces as a clear error at subscribe time rather than as corrupt data. A subscriber that omits the field is treated as pre-1.0 and rejected; third-party subscribers must send it.

  `bincode` is gone from dora's own dependencies; it remains in the tree only transitively via `zenoh-ext`. See [RUSTSEC-2025-0141](https://rustsec.org/advisories/RUSTSEC-2025-0141.html).
- **`dora-operator-api-cxx` operator interface gains `on_input_closed` and `on_stop`**: previously the C++ operator API silently dropped `Event::InputClosed { id }` and `Event::Stop` via a catch-all `_ => Continue` arm — operators had no way to react to upstream input closure or graceful shutdown. The cxx::bridge now declares two additional callbacks that the C++ side must implement:
  ```cpp
  DoraOnInputResult on_input_closed(Operator& op, rust::Str id, OutputSender& output_sender);
  DoraOnInputResult on_stop(Operator& op, OutputSender& output_sender);
  ```
  Both receive the same per-event `OutputSender` as `on_input`, so operators can emit a final/status output in response to the event (e.g. flush buffered state on stop, send a "drain complete" marker on input close). Without these symbols, downstream C++ operators that build against `dora-operator-api-cxx` will fail to link. To restore pre-change behavior in an existing operator, add stubs that ignore `output_sender` and return `{ rust::String(), false }`. See [#1849](https://github.com/dora-rs/dora/pull/1849) (rescue of [#1414](https://github.com/dora-rs/dora/pull/1414)).
- **Coordinator persisted-store `SCHEMA_VERSION` bumped `2` → `3`**: `DataflowStatus::Failed` gained a `terminal` field (#1854) without a matching schema bump, so schema `2` has silently meant two different, mutually incompatible on-disk record shapes: `v1.0.0-rc.1` stores (no `terminal`) and `v1.0.0-rc.2` stores (`terminal` included). bincode is not self-describing, so `#[serde(default)]` cannot backfill a missing trailing field the way it would for JSON — an rc.1-shaped `Failed` record read under the current type either fails to decode or (since `status` is not the last field of `DataflowRecord`) silently mis-decodes every field after it, and `list_dataflows`/`get_dataflow` were swallowing that failure with only a `warn!` log, so terminally-failed dataflows could silently vanish from `dora list` after a coordinator restart. `RedbStore::open()` now refuses to open **any** v2-stamped database with a `schema version mismatch` error — including rc.2 stores, whose row shape happens to still decode correctly, because schema `2` is ambiguous and the two shapes cannot be told apart from the version number alone. **If you have an existing coordinator store from `v1.0.0-rc.1` or `v1.0.0-rc.2`** (`~/.dora/` by default; `redb` is the default `--store` backend), `dora coordinator` will refuse to start after upgrading past this change. Delete the store file (its path is named in the error message) to start fresh, or pass `--store memory` to bypass persistence. See [#2471](https://github.com/dora-rs/dora/issues/2471).
- **Coordinator persisted-store `SCHEMA_VERSION` bumped `3` → `4`**: `DataflowRecord` gained `ready_barrier_released` and `barrier_exited_before_subscribe`, which persist whether a dataflow's start barrier has been released and with what verdict. The coordinator needs this because the in-memory `RunningDataflow` does not survive orphan reclaim (every daemon running the dataflow disconnecting) or a coordinator restart, and a daemon that missed the original `AllNodesReady` broadcast cannot ask for another — daemon-side `reported_init_to_coordinator` is set once and never reset — so without a durable record of the release its nodes park in `init_from_env()` for the life of the dataflow (#2998). As with the `2` → `3` bump above, bincode is positional rather than self-describing, so `#[serde(default)]` cannot backfill the added fields: a v3-shaped record read under the current type shifts every field after `uv` and mis-decodes into a structurally valid but wrong record. `RedbStore::open()` therefore rejects a v3-stamped database with a `schema version mismatch` error. **If you have an existing coordinator store written before this change** (`~/.dora/` by default; `redb` is the default `--store` backend), `dora coordinator` will refuse to start after upgrading. Delete the store file (its path is named in the error message) to start fresh, or pass `--store memory` to bypass persistence. See [#2998](https://github.com/dora-rs/dora/issues/2998) / [#3013](https://github.com/dora-rs/dora/pull/3013).
- **PyO3 bumped 0.28 → 0.29** (and `pythonize` 0.28 → 0.29, `arrow` floor `59` → `59.1`). This clears [RUSTSEC-2026-0176](https://rustsec.org/advisories/RUSTSEC-2026-0176) (out-of-bounds read in `PyList`/`PyTuple` iterator `nth`/`nth_back`) and [RUSTSEC-2026-0177](https://rustsec.org/advisories/RUSTSEC-2026-0177) (missing `Sync` bound on `PyCFunction::new_closure`), both fixed only in pyo3 0.29; neither affected API was reachable from dora, and the temporary audit waivers in `deny.toml` / `.cargo/audit.toml` are removed. The bump was gated on `arrow-pyarrow`, which required pyo3 `^0.28` through arrow 59.0 and moved to `^0.29` in 59.1 — `pyo3-ffi` declares `links = "python"`, so cargo permits exactly one copy in the dependency graph and the two must move together. **This is breaking for anyone linking against a dora crate that exposes pyo3 in its public API** (`dora-operator-api-python`, `dora-node-api-python`, `dora-ros2-bridge-python`, `dora-runtime-python`): a downstream still on pyo3 0.28 hits a duplicate-`links` resolution failure rather than a type error, so upgrade your own pyo3 to 0.29 at the same time. Users of the published `dora-rs` Python wheel are unaffected — the ABI floor is still `abi3-py311` and the Python-visible API is unchanged. See the [pyo3 0.29 migration guide](https://pyo3.rs/v0.29.0/migration.html) and [#2157](https://github.com/dora-rs/dora/issues/2157).
- **Python ABI floor bumped to `abi3-py311`** (from `abi3-py37`). The published `dora-rs` Python wheel now requires Python 3.11 or newer. This unblocks the new `send_output_raw` zero-copy send API (which depends on the stable buffer-protocol slots that became part of the C API in 3.11) and aligns with the 1.0 RC consolidation. Python 3.7, 3.8, 3.9 are all EOL; Python 3.10 EOLs October 2026. Users on Python 3.7–3.10 can stay on dora 0.5.0 during the transition. See [#1291](https://github.com/dora-rs/dora/pull/1291) / [#1833](https://github.com/dora-rs/dora/pull/1833).

### Added

- **`dora clean` subcommand**: removes fully-completed dataflows from the coordinator's state without restarting the coordinator. Candidates are enumerated from BOTH the in-memory `dataflow_results` map and the persisted store, so a restarted coordinator can still reap historical Succeeded/Failed rows that exist only on disk (the recovery loop intentionally does not reload completed dataflows into memory, so without this they would otherwise sit in redb forever). The coordinator deletes each cleaned dataflow from the persisted store first, then drops it from in-memory state; the redb deletion cascades to every `dora param` row owned by the cleaned dataflow so the on-disk state file doesn't grow unboundedly. Multi-daemon dataflows still finishing (some daemons reported, others haven't) are intentionally skipped so their final status is computed correctly when the last daemon completes. `finished_builds` is intentionally NOT touched (would break concurrent `dora build` calls with "unknown build id" errors). When the persisted-store delete fails for one or more candidates, the CLI prints a `warning:` line per failure to stderr and exits non-zero — those dataflows keep their in-memory entries so a later `dora clean` can retry, and the partial-outage state stays visible to scripted callers instead of being silently logged. If the persisted-store enumeration itself fails (e.g. an unreadable redb file), the coordinator hard-fails the request and leaves all in-memory state untouched, so the CLI never reports a misleading "nothing to clean" while historical rows are still on disk. Useful for dev workflows that accumulate dataflow history and for long-lived coordinators trimming redb state. Cleaned dataflows are no longer queryable via `dora logs <uuid>` or `dora param`. Rescue of [#1366](https://github.com/dora-rs/dora/pull/1366) (reimplemented against the current coordinator since the original PR targeted a control plane that was rewritten).
- **`node.send_output_raw(output_id, length, metadata=...)` — Python zero-copy send**: returns a `SampleHandler` that exposes dora's pre-allocated send buffer via Python's buffer protocol. The caller writes data directly into the buffer (`memoryview`, `numpy.asarray`, `struct.pack_into`) and either calls `.send()` or uses the context-manager form which sends on `__exit__`. Removes the one copy that `send_output(bytes_or_arrow)` performs to move Python-owned data into dora's send buffer — meaningful for camera frames, point clouds, and other MB-scale payloads at high rates. The handler enforces a safety contract: send-only-once, no view acquisition after `send()`, and `send()` refuses while buffer views are still open. See `examples/python-zero-copy-send/` for a runnable example. Rescue of [#1291](https://github.com/dora-rs/dora/pull/1291) / [#1833](https://github.com/dora-rs/dora/pull/1833).
- **Managed Python environments with `--uv`**: `dora build --uv` now creates a dedicated `uv` virtual environment per Python node at `<working-dir>/.dora/python-envs/<node-id>/` (for `.py` custom nodes with a `build:` block and runtime nodes with Python operators). Build commands run inside that venv with `VIRTUAL_ENV` set and the env's `bin/` (or `Scripts/` on Windows) prepended to `PATH`. `dora start` / `dora run` automatically reuse the same interpreter and runtime env at spawn time — build-time deps == runtime deps deterministically, no cross-dataflow or cross-node contamination, and subprocesses spawned from inside the node (`subprocess.run(["pip", ...])`, console scripts, `python -m pip`) all resolve from the managed env. Script-only Python nodes (no `build:` block) keep using the caller's ambient `uv` environment. Fail-closed under `--uv` when a managed env was expected but not recorded (e.g. stale session or non-`--uv` build), pointing users at `dora build --uv`. Rescue of [#1515](https://github.com/dora-rs/dora/pull/1515). See [#1820](https://github.com/dora-rs/dora/pull/1820).
- **`dora doctor` `uv` availability check**: surfaces `PASS uv: <version>` when `uv` is on PATH, `WARN` with install hint otherwise. WARN-not-FAIL because pure Rust/C++ users do not need `uv`. Part of [#1820](https://github.com/dora-rs/dora/pull/1820).
- **MAVLink 2 bridge** (`dora-mavlink2-bridge` extension + `dora-mavlink2-bridge-node` binary): Apache Arrow ↔ MAVLink 2 conversion for the common dialect (HEARTBEAT, SYS_STATUS, SYSTEM_TIME, ATTITUDE, ATTITUDE_QUATERNION, LOCAL_POSITION_NED, GLOBAL_POSITION_INT, GPS_RAW_INT, RC_CHANNELS, SERVO_OUTPUT_RAW, COMMAND_LONG, COMMAND_ACK, MISSION_CURRENT). TCP/UDP/serial transports, daemon-spawnable bridge node, and a self-contained `examples/mavlink2-bridge` dataflow with an in-process UDP simulator (no SITL/MAVProxy required). The example ships three consumer variants — Rust (`dataflow-rust.yml`), Python (`dataflow-python.yml`, `--uv`), and C++ (`dataflow-cxx.yml` via `cargo run --example mavlink2-bridge-cxx`) — all reading the same `bridge/heartbeat` Arrow output. See [#1786](https://github.com/dora-rs/dora/issues/1786).
- **`examples/mavlink2-bridge-sitl-mission`**: closed-loop ArduCopter SITL demo. A Python dora node arms, takes off, hovers, lands, and disarms a simulated multirotor by driving the bridge's `command_long_cmd` input and watching `command_ack` + `global_position_int`. Local-only on Ubuntu / macOS; not part of CI (SITL needs a one-time ArduPilot install per developer machine). See `examples/mavlink2-bridge-sitl-mission/README.md`.

### Fixed

- **Nodes no longer outlive a SIGKILLed `dora run`** (Unix): an in-process daemon (`dora run`, `dora daemon --run-dataflow`, and embedders driving `Daemon::run_dataflow`) now hands every node it spawns the run process's pid (`DORA_RUN_PARENT_PID`), and the node API's orphan guard — armed at the top of `init`, before anything that can block — SIGKILLs the node's **own process group** once that pid is gone. The whole group on purpose: under `--uv` the tracked process is a wrapper (`uv run python ...`) and ending only the caller would leave the interpreter orphaned one level down. Previously such nodes ran forever at `ppid 1` in a group of their own, unreachable by inherited signal delivery or a group-kill of the CLI, because nodes are deliberately spawned as process-group leaders and a node that is not polling its event stream never observes the daemon-socket EOF. Scoped to in-process daemons only: the `dora up` + `dora start` path injects nothing, so nodes there still survive daemon restarts (#2029). The variable is control-plane-denylisted — a descriptor cannot forge it and a stale shell export cannot leak it. Known gaps, tracked on the issue: a process killed before it reaches `init` (a Python node still in `import torch`), `path: shell` commands that never call `init`, and Windows (left to the daemon's Job Object wrap). See [#2856](https://github.com/dora-rs/dora/issues/2856) / [#3018](https://github.com/dora-rs/dora/pull/3018).

## 0.1.0 (2026-03-13)

First official release of Dora (AI-Dora) -- a 100% Rust framework for building real-time robotics and AI applications.

### Highlights

- **10-17x faster than ROS2 Python** with zero-copy shared memory IPC and Apache Arrow native data format
- **Multi-language support** -- write nodes in Rust, Python, C, or C++ with native APIs
- **Declarative YAML dataflows** -- define pipelines as directed graphs with typed inputs/outputs
- **Single CLI for full lifecycle** -- build, run, monitor, record/replay, and distributed deployment

### Core Framework

- Coordinator/daemon architecture for distributed multi-machine deployments
- WebSocket control plane (single port for CLI and topic data)
- Shared memory transport for messages >= 4KB (zero-copy)
- Zenoh pub-sub for cross-machine communication
- Apache Arrow columnar format throughout (zero serialization overhead)

### Fault Tolerance

- Per-node restart policies (never/on-failure/always) with exponential backoff
- Passive health monitoring for hung node detection
- Per-input circuit breakers with configurable timeouts and auto re-subscription
- Coordinator state persistence via redb

### Communication Patterns

- Topic (default pub/sub)
- Service (request/reply with correlation IDs)
- Action (goal/feedback/result with cancellation)
- Streaming (session/segment/chunk for voice and real-time apps)

### Logging and Observability

- Unified logging with `dora/logs` virtual input and OTel propagation
- Structured output with filtering, rotation, and log routing
- `dora top` TUI for per-node CPU, memory, queue depth, network I/O
- `topic echo/hz/info` for live data inspection
- `trace list/view` for coordinator span inspection
- Record/replay to `.drec` files with node substitution

### CLI

- `dora run` for local dev, `dora up/start` for distributed prod
- `dora record/replay` for dataflow debugging
- `dora cluster up/status/down` for SSH-based fleet management
- `dora node info/restart/stop`, `dora topic pub`
- `dora doctor` for environment diagnostics
- `dora status --json` for programmatic access
- Configurable queue policies (`drop_oldest` / `backpressure`) per input

### Module System

- Reusable sub-graphs as standalone YAML files
- Typed inputs/outputs with parameters and nested composition
- Optional type annotations with build-time static validation

### ROS2 Bridge

- Bidirectional topic, service, and action bridging
- Declarative YAML configuration
- Per-topic QoS override

### Developer Experience

- Hot reload for Python operators
- In-process operators for lightweight functions
- Comprehensive examples (15+ dataflows)
- mdBook user guide (English and Chinese)
- GitHub Actions CI with cross-platform testing

### Security

- Bearer token authentication (opt-in)
- Per-IP WebSocket rate limiting
- Path traversal guards, input validation, error sanitization
- Resource limits and bounded data structures
